## Top 10 Quick-Win Performance Improvements (ranked by ROI)

1. **Eliminate duplicate Base64 decode in `Base64DecodingService.decodeAndSaveFile`** — P1, trivial change, real memory/CPU savings on every `/save-decoded` call.
2. **Eliminate duplicate Base64 decode in `PdfProtectionServiceImpl.decodeAndValidate`** — P1, trivial change, real savings on every `/pdf/protect` call (up to 20MB payloads).
3. **Remove the no-op `.replaceAll("\\r|\\n", "")` in `PdfService.fetchAndConvertToBase64Dynamic`** — P1, removes a hidden regex compile+scan on every dynamic fetch.
4. **Hoist the filename-extraction `Pattern.compile` to a static field in `PdfService.detectFileName`** — P1, standard regex-in-loop-equivalent fix.
5. **Stream large file downloads instead of `Files.readAllBytes` in `FileStorageFacade`/`DecodedFileController`** — P2, biggest memory-pressure fix under concurrent large-file traffic.
6. **Share a single `encodeBody(byte[])` helper between `PdfService`'s two encode call sites** — P2, prevents the class of bug that produced finding #3 from recurring.
7. **Consolidate the three duplicated short-UUID snippets into one shared helper** — P3, minor CPU/allocation win, real maintainability win.
8. **Route batch `/convert` through the existing `fileExecutor` async path** — P3, largest *latency* win available, but requires explicit review of partial-failure semantics before implementing (not a same-sprint quick win).
9. **Consider buffering/batching the per-request audit-log `Files.write(..., APPEND)` calls** — P3, only matters at sustained high volume.
10. **(Confirmatory, not a change) Verified `RestTemplate`, `ObjectMapper`, and `Tika` are all already correctly singleton-scoped** — ROI here is negative-cost: no work needed, but worth stating explicitly so this isn't re-investigated in a future review.

## Top 10 Memory Optimizations
Findings #1, #2, #5 above are the only genuine memory-allocation findings this review turned up (duplicate decode buffers, and one un-streamed large-file response path). The codebase is otherwise disciplined about memory: no unbounded in-memory caches were found (`asyncResults`/`asyncResultTimes` in `FileConversionService` are `ConcurrentHashMap`s with a scheduled hourly eviction based on `file.cache.retention-hours`), and file processing already writes to disk rather than holding multiple large buffers in memory simultaneously (see `FileConversionService.handleFileProcessing`: download-to-disk, then a single `readAllBytes` for encoding, not multiple parallel copies).

## Top 10 File-Processing Optimizations
Covered by findings #1, #2, #5, #9 above — this is a small codebase with a small file-processing surface area (three services touch disk I/O: `FileConversionService`, `Base64DecodingService`, `Base64OutputWriter`/`FileStorageFacade`), and each was read in full. No temp-file leak was found — every temp-file path (`FileConversionService.handleFileProcessing`'s `tempFile`) has a corresponding `Files.deleteIfExists`/`safeDelete` on both success and failure paths.

## Top 10 Logging Optimizations
Only one item survived scrutiny as a genuine logging-performance finding, and it was already fixed in a prior session (see `LoggingInterceptor.logResponse`'s `isDebugEnabled()` guard around a body-buffering read — confirmed present, not re-flagged as new). No new expensive-logging pattern (large payload serialization, unconditional `objectMapper.writeValueAsString` for logs, Base64 content in log lines) was found anywhere in this pass. This section is intentionally short because the codebase's own prior logging remediation already closed the obvious findings this task's prompt was checking for.

## Top 10 HTTP Client Optimizations
Only finding #3 (redundant regex on Base64 output) touches the HTTP-response-handling path. The `RestTemplate`/`HttpClient` configuration itself (`UnsafeRestTemplate`) is already production-appropriate: pooled connections (200 total/20 per-route), configurable timeouts, idle-connection eviction every 2 minutes, and a `BufferingClientHttpRequestFactory` wrapper needed for the existing logging interceptor to read the body without consuming the stream. No changes recommended to the HTTP client configuration itself.

## Final Verdict

# IMPLEMENT SELECTIVELY

**Justification, per recommendation:**

- **Findings #1–#4 (P1): APPROVE FOR IMPLEMENTATION.** All four are mechanical, behavior-preserving fixes (remove a redundant decode/encode/compile) with no business-logic change, no new dependency, and a test suite already in place (`PdfProtectionServiceImplTest`) to catch any regression. These are exactly the "quick win, same sprint" class this review scoped for.
- **Finding #5 (P2, streamed downloads): APPROVE FOR IMPLEMENTATION**, with the one caveat that the `Content-Disposition`/`Content-Length` header-setting logic in `DecodedFileController.downloadDecodedFile` needs to be re-verified after switching to `Resource` (Spring computes `Content-Length` differently for streamed resources) — low risk, but worth a manual download test before merging, not a blind swap.
- **Findings #6–#7 (P2/P3, shared helpers): IMPLEMENT SELECTIVELY** — genuinely low-risk but purely maintainability-driven (negligible runtime gain); bundle with unrelated work rather than a dedicated change.
- **Finding #8 (P3, async batch): DO NOT IMPLEMENT THIS SPRINT** despite being the largest theoretical latency win — it changes concurrent-execution and partial-failure semantics for a widely-used batch endpoint, which is explicitly outside this review's "no business-logic change" boundary and needs its own design conversation (error aggregation, thread-pool contention with the PDF-protection endpoint that shares no pool today but would need to be considered), not a quick-win merge.
- **Finding #9 (P3, audit-log batching): DO NOT IMPLEMENT THIS SPRINT** — changes on-disk audit file format/timing, and this codebase's audit trail may already be consumed by something downstream (not verified in this source-only review) — needs a stakeholder check first, not a source-level judgment call.

**Net recommendation:** implement findings #1–#5 in this sprint (all low-risk, all source-file-local, all covered by or easily added to the existing JUnit suite); defer #6–#9 as tracked follow-ups, not urgent.
